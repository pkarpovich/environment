# Local object storage

One SeaweedFS with the S3 gateway serves the whole Mac at `https://s3.localhost`. A local service that stores objects uses it and never a production bucket. It accepts only tokens of the local authorization server, so nothing that works here is valid anywhere else.

It runs the image production runs, as the compose project `seaweedfs` in `~/.local/share/seaweedfs`. Docker restarts it, foster does not run it, and its route is the `s3.localhost` line in `static.map`. Nothing in that directory is in a repository.

| Path in `~/.local/share/seaweedfs` | What it is |
|---|---|
| `compose.yml` | SeaweedFS, port `50920` on loopback |
| `config/iam.json` | the identity provider, and one policy and one role for each service |
| `config/secrets/sts.env` | the key that signs temporary credentials, made once |
| `data/` | the objects |

What a service needs to know about the storage:

| | |
|---|---|
| endpoint | `https://s3.localhost` |
| audience of the token | `https://seaweedfs-s3` |
| role | `arn:aws:iam::role/<service>` |

## How a service gets in

There are no static keys. The service asks the local authorization server for a token with the `client_credentials` grant, audience `https://seaweedfs-s3` and scope `s3:<service>`. It trades that token for temporary keys with `AssumeRoleWithWebIdentity` on the same endpoint, and signs its S3 requests with them. The role decides which buckets the keys open.

## A role for a service

1. In the local authorization server, give the service's client the `client_credentials` grant, the scope `s3:<service>` and the audience `https://seaweedfs-s3`. See `auth.md`.
2. In `config/iam.json`, add a policy that names the bucket, and a role that trusts the client. Copy the `heap` pair and change the names:

   ```json
   {
     "roleName": "heap",
     "roleArn": "arn:aws:iam::role/heap",
     "attachedPolicies": ["heap"],
     "trustPolicy": {
       "Version": "2012-10-17",
       "Statement": [
         {
           "Effect": "Allow",
           "Principal": { "Federated": "*" },
           "Action": ["sts:AssumeRoleWithWebIdentity"],
           "Condition": {
             "StringEquals": { "oidc:iss": "https://auth.localhost", "oidc:sub": "heap" }
           }
         }
       ]
     }
   }
   ```

   `oidc:sub` is the client id in the local authorization server.
3. Restart from `~/.local/share/seaweedfs`: `docker compose restart seaweedfs`.
4. Point the service at the storage in its own environment: the endpoint, the role and the client it asks tokens with.

## Checking that it works

```sh
curl -s -o /dev/null -w '%{http_code}\n' https://s3.localhost/healthz
docker exec seaweedfs wget -qO- https://auth.localhost/jwks.json
```

The first prints `200`. The second prints the keys of the authorization server: if it fails, the storage cannot check any token. A service that assumes its role then starts with its storage check green, and an upload lands.

To read one object without credentials, ask the filer inside the container: `docker exec seaweedfs wget -qO- http://127.0.0.1:8888/buckets/<bucket>/<key>`.

## Facts that cost time once

- SeaweedFS fetches the keys of the authorization server itself, from inside its container. Authelia answers `/jwks.json` only to a request that came through the proxy, so the container resolves `auth.localhost` to the host gateway and trusts Caddy's root certificate, which `compose.yml` mounts read-only.
- Loading `iam.json` turns authorization on for every request to the S3 endpoint. The filer port inside the container still answers reads without credentials, and it is not published.
- A role is tied to a client id, not to a scope. A renamed client loses its role until `oidc:sub` follows.
